## Write-path classification (who creates rows)

- **REAL_RAZORPAY rows**: only `SyncService` upserts (`services/merchant/service.py`) — orders/payments/subscriptions/payment-link-embedded payments, stamped `source_type=razorpay_test|razorpay_live`, `source_system=razorpay`, `external_id`, `ingested_at`. Idempotent on `(source_type, external_id)` — proven live (`0 created · 6 updated`).
- **REAL_WEBHOOK rows**: `payment_events` are written ONLY by `services/recovery/webhook_handlers.py:298-309` (verified: sole constructor). **REST sync never writes payment events** — the root cause of the real_test analytics starvation.
- **SYNTHETIC_SIMULATOR rows**: simulator seed path (`app/simulator/*`, demo router, seed scripts), all `source_type=simulator`, environment `research`.
- **REAL_DATABASE rows**: sync_runs, connection_state, audit_logs, policy_decisions, recovery_*, webhook_events, notification_outbox — the app's own bookkeeping.
- **DERIVED**: dashboard summaries, revenue-at-risk figures, evaluation metrics — computed from the above; every "recoverable/expected" rupee figure derives from a **prior** recoverability table (`services/revenue/config.py`), not measured conversion.
- **FIXTURE/MOCK**: confined to `backend/tests/**` (conftest pins blank Razorpay keys) and the in-repo `SimulatedPaymentGateway` used by the Research Lab. No mock data in the frontend (grep-verified).

## Leak analysis (can synthetic leak into real views?)

- Environment isolation is enforced by `source_type`-scoped queries in detection (`series.py:192`), revenue engine, insights, builder, dashboard — fixed and test-covered 2026-09-01 (`tests/revenue/test_environment_scoping.py`, `tests/insights/test_environment_scoping.py`).
- **One latent seam remains**: diagnosis feature loading `load_window_records` (`services/diagnosis/features.py:144-149`) filters by time only — no environment scope. Inert only because diagnosis runs on incidents, which are themselves environment-scoped. Latent, not active.
- Fail-safe default: unknown source_types map to `research` (architecture agent verified).

## Findings

- **[HIGH] D-REAL-1 — The real_test analytics path is structurally starved.** Payment entity rows exist; the event stream that detection/dashboard/diagnosis consume is only writable by webhooks (and the simulator). Until Razorpay webhook deliveries flow continuously, the entire real merchant analytics story is empty by construction.
- **[MEDIUM] D-REAL-2 — Prod first impression mixes a full Research Lab with an empty merchant view** — the only populated datasets on the deployment are synthetic; the Evaluation Lab's single stored run shows negative lift. Honest labels exist, but a judge's first 60 seconds are defined by this split.
- **[LOW] D-REAL-3 — `incidents.revenue_at_risk_paise` changes methodology between list (gross affected-sum) and detail (counterfactual observed-loss) views** — audited swap, but potentially confusing.
- **[INFO] No FIXTURE/MOCK/HARDCODED data can reach production views** — all such paths are test-only or Research-Lab-only and labeled.
